Необходимо использовать возможности оценки освещения ARFoundation.Для ARKit (приоритет iOS) можно получить доступ к интенсивности окружающего света (общая яркость) и цветовой температуре.24Шейдер будет принимать эти значения в качестве входных данных. Это гарантирует, что белая стена, окрашенная виртуальной белой краской, будет выглядеть правильно как при желтом свете лампы накаливания, так и при синем дневном свете.253.2 Продвинутое применение: Проецирование текстур с помощью DecalsВместо попыток генерировать новую геометрию или манипулировать AR-сеткой, наиболее эффективным и гибким способом "окрашивания" стен является использование Decal Projectors.27Принцип работы: Decal Projector проецирует материал (наш пользовательский PBR-материал краски) на существующую геометрию в пределах определенного объема, подобно реальному проектору.30 Это позволяет избежать сложных UV-разверток или манипуляций с сеткой.Реализация:Когда пользователь касается стены, будет создан экземпляр компонента Decal Projector из префаба.Проектору будет назначен наш PBR-материал краски, настроенный с выбранным цветом и отделкой.Объем проектора будет изменен и сориентирован так, чтобы покрывать сегментированную область стены. Сама маска сегментации будет использоваться для контроля формы декали, гарантируя, что она "красит" только стену.Этот подход очень эффективен, особенно в URP, и позволяет накладывать несколько эффектов (например, краску, а затем виртуальную рамку для картины сверху).29Симуляция текстуры: Для добавления большего реализма можно включить в наш PBR-материал краски тонкую карту нормалей, которая симулирует текстуру валика ("шагрень").21 Эта небольшая деталь значительно улучшит визуальную достоверность при просмотре с близкого расстояния.Раздел 4: Устранение нестабильности: Временная согласованность и постобработкаЭтот раздел напрямую решает проблему "бегающих пикселей", которая является серьезным препятствием для профессионального пользовательского опыта.4.1 Диагностика "мерцания": Проблема временной когерентностиМерцание — это классический симптом отсутствия временной согласованности. Каждый кадр из видеопотока обрабатывается ML-моделью независимо.32 Даже незначительные изменения в освещении, угле камеры или шуме сенсора между кадрами могут привести к тому, что модель по-разному классифицирует отдельные пиксели, что приводит к шумному, "кипящему" эффекту на краях маски.34Это хорошо известная проблема в семантической сегментации видео (VSS).32 Продвинутые решения часто включают сложные методы, такие как оптический поток 33 или временные модели на основе трансформеров 32, которые слишком вычислительно затратны для нашего случая использования на мобильных устройствах в реальном времени.4.2 Надежное и легковесное решение: Фильтр Калмана для стабилизации маскиРешение проблемы мерцания заключается не в поиске идеальной модели, а в отделении задачи стабилизации от задачи сегментации. Идеальным решением является настоящая VSS-модель, но они ресурсоемки. Необходимо решение, которое работает с текущей покадровой моделью и будет работать с будущей. Это предполагает этап постобработки. Нужен легковесный алгоритм, который может использовать историю предыдущих масок для предсказания и сглаживания текущей. Фильтр Калмана идеально подходит для этой задачи.41 Это рекурсивный оценщик, который чрезвычайно эффективен и отлично справляется с предсказанием состояния системы (в нашем случае, формы маски сегментации) на основе серии зашумленных измерений (сырых данных от ML-модели). Внедрение фильтра Калмана в качестве модуля постобработки позволяет решить проблему стабильности независимо от процесса выбора ML-модели. Это дает стратегическое преимущество, позволяя команде значительно улучшить UX в краткосрочной перспективе (Фаза 1 дорожной карты), в то время как более трудоемкая работа по выбору и дообучению новой модели будет происходить параллельно (Фаза 3).Стратегия реализации:Представление состояния: Фильтрация всей пиксельной маски нецелесообразна. Вместо этого граница маски будет представлена упрощенным набором контрольных точек (например, полигоном). Вектор состояния (X) для нашего фильтра Калмана будет содержать положения и скорости этих контрольных точек.42Шаг предсказания: В каждом кадре, до получения новой маски сегментации, фильтр Калмана будет предсказывать новые положения контрольных точек на основе их предыдущих положений и скоростей. X_predicted = F * X_previous.44 Это дает нам сглаженную, ожидаемую форму маски.Шаг обновления: Когда приходит новая, зашумленная маска от ML-модели, из нее извлекаются граничные точки (измерение, M). Затем состояние фильтра обновляется путем смешивания предсказания с новым измерением, взвешенным по коэффициенту усиления Калмана (K). X_new = X_predicted + K * (M - H * X_predicted).44 Коэффициент усиления рассчитывается на основе неопределенности нашего предсказания по сравнению с неопределенностью измерения, эффективно отфильтровывая шум.43Результат: На выходе получается новый набор контрольных точек, представляющий собой временно сглаженную версию маски. Этот полигон затем используется для рендеринга финальной, стабильной маски. Этот подход вычислительно дешев и высокоэффективен для устранения дрожания.46Упрощенная логика фильтра Калмана на C# (иллюстрация):C#// Будет реализовано в новом классе 'MaskStabilizer'
public class MaskStabilizer 
{
    private KalmanFilter2D controlPointFilters; // Один фильтр на каждую контрольную точку

    public Point StabilizeMask(Point noisyControlPoints) 
    {
        if (controlPointFilters == null) {
            InitializeFilters(noisyControlPoints);
        }

        Point stabilizedPoints = new Point[noisyControlPoints.Length];
        for (int i = 0; i < noisyControlPoints.Length; i++) 
        {
            // 1. Предсказать, где должна быть точка, на основе прошлой скорости
            Point predictedPoint = controlPointFilters[i].Predict();

            // 2. Обновить предсказание новым зашумленным измерением
            Point correctedPoint = controlPointFilters[i].Update(noisyControlPoints[i]);

            stabilizedPoints[i] = correctedPoint;
        }
        return stabilizedPoints;
    }
}
Раздел 5: Погашение технического долга: Унифицированная и масштабируемая архитектураВ этом разделе представлен конкретный план рефакторинга архитектуры приложения, направленный на решение критических проблем двойной системы отображения, разрыва между симулятором и устройством, а также общих узких мест в производительности.5.1 Унификация представления: Паттерн Model-View-Presenter (MVP)Текущий конфликт между Legacy SegmentationDisplay и ARWallPresenter является классическим симптомом плохого разделения ответственности. Логика управления данными сегментации переплетена с логикой их отображения.Система будет переработана с использованием паттерна Model-View-Presenter (MVP), который хорошо подходит для разработки на Unity.52Model: Новый набор простых C#-классов, отвечающих за хранение данных сегментации (например, сырой текстуры маски, стабилизированных контрольных точек). Модель ничего не знает о том, как эти данные отображаются.View: MonoBehaviour ARWallPresenter. Его единственная задача — рендерить данные, предоставленные ему Presenter'ом. Он будет содержать Decal Projector и PBR-материал. Он не должен содержать сложной логики.Presenter: Логика, находящаяся в настоящее время в AsyncSegmentationManager.cs. Он будет отвечать за координацию всего: получение кадров с камеры, отправку их в движок Sentis, получение сырой маски, передачу ее в MaskStabilizer (фильтр Калмана) и, наконец, получение финальных, стабильных данных из Модели и передачу команды View на их отображение.Преимущество: Это чистое разделение немедленно решает проблему двойной системы. Существует только одно View (ARWallPresenter). Это также делает систему тестируемой и более простой для отладки.5.2 Преодоление разрыва между симулятором и устройствомПроблема пользователя, связанная с тем, что маска не отображается в редакторе Unity, является прямым следствием тесно связанной архитектуры. Текущая система, вероятно, имеет жесткую зависимость от XRCpuImage из живого потока AR-камеры, который недоступен в редакторе.Решение с помощью MVP: Паттерн MVP элегантно решает эту проблему. В редакторе можно создать "мок"-Presenter, который вместо использования живой камеры просто загружает статическое изображение или предварительно записанный видеофайл. Он прогоняет его через конвейер сегментации и стабилизации и передает результирующие данные Модели в тот же самый View ARWallPresenter.Результат: Логика рендеринга может быть полностью разработана и протестирована в редакторе, что значительно ускоряет цикл разработки PBR-шейдера и системы декалей. Поведение в редакторе теперь будет соответствовать поведению на устройстве.5.3 Фундаментальные оптимизации UnityК кодовой базе будут применены стандартные лучшие практики производительности Unity, как описано в официальных руководствах.55Кэширование ссылок: В ARWallPresenter и AsyncSegmentationManager будет обеспечено, чтобы все вызовы GetComponent<T>() выполнялись один раз в Awake() или Start(), а результаты кэшировались в приватных переменных-членах, чтобы избежать повторных, затратных вызовов в циклах Update().55Обработка текстур: Пользователь отметил "Множественные пересоздания текстур".
